# Codex host configuration access restoration

The application owns the complete best-effort restoration flow through eight
required synchronous ports. Docker retains native config/access/metadata/UID/
repair/warning composition and the historical void export/name/arity2. Fresh
native scope per public call captures access mode once after config resolution,
before the first try, and reuses it for host recheck. Construction observes none
of those effects; resolving config and mode failures escape both catches.

Initial access success returns. Read caught code directly: ENOENT returns,
EACCES/EPERM proceed, all other values warn and return. Nullish/code-getter or
initial-warning failures escape. Do not normalize unknown errors or add a catch.

Repair checks host identity availability, then observes parent and config before
any predicate. Preserve parent directory receiver, UID getter, live process UID
invocation and config file receiver in original short-circuit order. Host nlink
is not a restoration predicate. Native ACL scripts retain their separate checks.

Native repair preserves outer runtime selection before the UID helper's inner
runtime selection, exact commands/encoding/15-second timeout and diagnostics.
The host config path does not enter its fixed in-container ACL script. UID parsing,
mutation wrapper, descriptors/principals and lock ownership remain unchanged.
Successful repair rechecks access; repair/recheck errors warn with the original
path/reason. Warning conversion or reporting can still throw as before.

Keep preparation, startup/MCP/profile locks, harness finally restoration and
post-command env/session cleanup callsites unchanged. Verify ordered errno/getter/
predicate/fault traces, actual public native-boundary fixtures and both shipped
payloads with emitted declarations. Real credential material is never a fixture.

## Known ceiling

This is host access restoration, not ordered directory/file preparation, profile
migration or new ACL/mount/UID authority. Existing native races, rootless mappings,
SELinux/remote/native OS and real runtime acceptance remain separate. Returned
warnings are not an authentication or successful-access certificate.
