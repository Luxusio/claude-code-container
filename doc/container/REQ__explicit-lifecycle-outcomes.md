# Explicit container stop/remove outcomes

Derived from the existing [architecture outcome and authority contracts](../common/SPEC__ccc-architecture-contracts.md), these requirements correct lost cleanup results and mutable target selection in the explicit CLI stop/remove operation. They do not define a new resource manager or storage schema.

Resolve the project once before acquiring its existing lifecycle lock. The same absolute path and profile select the claim prefix, name, managed identity proof, cleanup owner and presentation. After proof, copy the unique container ID and initial running flag before invoking cleanup or reporting callbacks. Those callbacks cannot redirect the operation or change whether its captured running container requires a stop.

Raw claims remain inside the lock; nonempty claims require exactly `force:true`. Force never bypasses managed identity. Confirmed absence causes no cleanup or destructive command. Unknown, foreign or failed ownership proof keeps the existing refusal behavior. Runtime authority stays captured for the exact-ID commands, which retain their existing arguments, timeout, stdio and plain removal policy.

The reusable application returns a specialized result containing initial target facts, normalized cleanup summary and separate stop/removal command facts. Cleanup reports expose counts of stopped, skipped and failed devices, never raw command strings, output, helper errors or paths. A thrown cleanup becomes unavailable, with no invented partial counts. Failed/unavailable cleanup emits a bounded warning and still permits the authorized container action.

Clean native exit zero without error or signal acknowledges a command; every other returned receipt is unconfirmed. Unconfirmed stop prevents removal and stopped/removed messages. Unconfirmed removal retains earlier acknowledged stop and cleanup facts. Native uncertainty takes precedence over cleanup-only incompleteness. Initial identity and command acknowledgement are separate observations; the result does not claim a fresh post-command inspection or rollback.

The lock synchronously returns its callback's closed application result. Native composition consumes that result and retains public void signatures. Accepted container action with incomplete cleanup keeps exit status zero and its warning; native command failure keeps the existing bounded error and nonzero CLI exit. No automatic replay, compensation, new force flags or broad cleanup is introduced. Warning, identity, readiness, lock and unexpected native/programming exceptions retain their existing propagation; there is no promise of a universal post-effect recovery ledger.

Verification uses existing core/type/native facade owners, Docker regressions and the two direct emitted consumers. Fix fixture inventory so managed and foreign tests inspect an actual selected ID rather than accidentally observe absence. Old-source witnesses demonstrate lost cleanup warnings or redirected mutable identity without an ABI failure. A fenced emitted composition exercises accepted action plus incomplete cleanup and native uncertainty. Portable checks do not establish real engines, native Windows/macOS or whole architecture completion.
