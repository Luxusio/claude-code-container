# Session admission with retained predecessor responsibility

Status: active, 2026-10-26.

A dead session can retain an uncertain native startup request. Its record is unresolved cleanup evidence, not proof of a live session. An unrelated new invocation must not discard it merely because processes or containers appear absent.

- Reconcile first under the project lifecycle guard. Only structurally qualified pending-only recovery failures may offer restricted admission: unchanged monitored receipt and observation, positively stale owner and guardian, explicit pending request without current cleanup authority, and the same captured native runtime. Mixed failures and unknown, replaced, unreadable or foreign-runtime evidence remain fatal.
- Restricted admission requires a freshly identified managed full container ID bound to the same project/runtime and an explicit running or stopped state. Static stopped admission may require live verification. Recheck the same ID before guardian acknowledgement, after reconciliation, at execution status, immediately before any start and at ready handoff. Missing or changed targets refuse admission.
- The restriction remains for the whole invocation even if later reconciliation succeeds. Preserve predecessor main records, sidecars, generations and all replacement/shared cleanup/exact-stop vetoes. Do not convert delayed daemon work into settled responsibility.
- Native preparation captures the existing immutable image by read-only inspection and defers image upgrades; it must not build or pull an image. The image digest pins the existing image, not its provenance or account contents. Current managed/project/mount/device/privilege and host user identity checks still apply. Do not fall back to weaker contract deferral after a definite mismatch.
- Permit only an exact-ID start of that existing compatible stopped target. Reuse stopped static preflight and require exec readiness, full live contract and effective UID/GID proof before setup or commands. Disable inherited proof-helper creation fallback in this restricted path. Never fall through to creation, replacement, removal, retained-state migration or creation-ticket preparation, including retries.
- Starting an existing target does not grant cleanup permission. Keep the new claim cleanup-disabled through initial acknowledgement, readiness, command launch, signals and exit. This bounded same-ID activation is an explicit exception to the general pre-start intent rule in the linked stopped-container-upgrade requirement: do not publish a generic creation/migration startup intent or own-start cleanup authority, because no new resource or cleanup obligation is acquired. Retire only the new qualified no-obligation claim and its guardian; preserve every predecessor. A start timeout or failed live proof permits no compensating stop, deletion or guessed cleanup.
- Allow normal guarded setup and user commands after live verification on the pinned target. The restriction is on container lifecycle effects, not read-only development filesystems. Reject unexpected owned-ready or own-start authority callbacks. Failed restricted acquisition rolls back only its qualified new reservation and guardian immediately; preserve the primary failure.
- Emit a bounded warning distinguishing retained recovery evidence from active sessions and explaining exact-target activation, deferred updates and disabled replacement/automatic cleanup. Other inspection, reservation, guardian and publication failures retain their actual errors.

Verification covers a genuinely stopped inspection and status, provisional stopped-to-live proof, exact-ID start, unchanged running reattachment, two retained pending predecessors, disabled acknowledgements through real guardian/publication/claim paths, own-only retirement and native preparation without producers or migration. Mixed failures, changed receipts/runtime/target/image, missing/unmanaged targets, unsafe identity/mounts, timeouts, failed live proof, late retries and unexpected ownership callbacks must preserve predecessor evidence and avoid replacement/cleanup effects. Existing administrative removal vetoes remain.

## Known ceiling

This path requires an existing compatible managed container. It does not create a missing environment, migrate incompatible retained state, settle historical uncertain obligations, or prove actual macOS/Windows acceptance from portable fixtures. Image updates remain deferred during restricted recovery.
