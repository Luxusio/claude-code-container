# Requested tool setup

`createRequestedToolSetup` owns supported Claude and Codex setup order. `ensure(target, activeTool)` first ensures the Claude launcher for Claude or installs the selected npm tool for Codex. It then probes the launcher and, only after successful Codex readiness, ensures the Codex sandbox. Container installation remains in the accepted container-tool installation application and its native bindings.

The Claude probe uses the domain launcher path. Codex uses `/home/ccc/.local/bin/` plus the configured binary, falling back to the tool name. The native `ensureTools` composition executes the launcher check through the selected container runtime with a 15000 ms timeout. Timeout produces a specific readiness error; any other probe error or nonzero status reports that the requested tool is unavailable after setup. Failed readiness prevents sandbox preparation.

Four required effect ports—`ensureClaudeLauncher`, `ensureNpmTool`, `ensureLauncherReady` and `ensureCodexSandbox`—return `undefined`, so ordinary asynchronous implementations cannot satisfy their synchronous completion contract. Native wrappers call the existing installation or sandbox function and then return `undefined`. `ensureLauncherReady(target, path, originalTool)` performs one native probe and throws the existing readiness error on failure. Only the native `ETIMEDOUT` error code means timeout; statuses 124 and 137 remain unavailable. The native binding reads the original tool name after a failed probe when constructing that message. The application receives the canonical descriptor directly; it neither snapshots nor freezes its mutable behavior.

The application owns installation, launcher selection and sandbox order. Native status/error decoding and CLI wording stay in `ensureTools`. Unexpected thrown values propagate without retry or wrapping, and failed readiness never proceeds to sandbox setup. The public `ensureTools` return and error behavior remain unchanged; injected internal factory bindings must use the required `ensureLauncherReady` effect instead of the former raw `probeLauncher` observation.

The existing core, facade and type-contract owners verify this seam. Workspace package smoke checks loading and packaged layout; it does not itself execute requested-tool readiness. Real compiled startup verification uses a container engine and is separate from these portable tests.

Container loss, restart and readiness recovery belong to the separate index/container-exec workflow. Requested-tool setup does not take over that recovery or add another container lifecycle. The retained conditional OpenCode prelude is outside the supported Claude/Codex scope and remains untouched; this contract correction does not establish unrestricted whole-tool completion.
