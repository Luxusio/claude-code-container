# Mobile application management

`createAndroidAppManagement` and `createIosAppManagement` expose `request(name, args)` and own admission and defaults. Android uses a finite semantic app effect and an opaque guarded target; its required `perform` port returns a finite success/failure observation with the original diagnostic receipt. The existing Android backends own ADB argv, launch-output interpretation and public presentation. iOS app management still constructs commands and interprets results through its existing session, container and publication ports; its remaining native boundary is a separate migration scope. Existing public request normalization and broker Appium routing remain in the inward request peer.

Android emulator and physical-device bindings retain owner, target, prerequisite and physical-lease checks before effects. Native execution qualifies each ADB command with the selected serial. Only installation carries the optional helper timeout, with the existing native truthiness, normalization and 300000 ms cap. The application selects component before package for launch, defaults direct install replacement to true while honoring false, and always replaces for the mobile alias. Native execution rejects launch diagnostics even when ADB exits zero; the application consumes that failed observation. Emulator stop/reset and physical package-name results keep their distinct presentation. The native presenter receives the original request name to distinguish physical app-data clearing from `device_reset`; app-data clearing does not imply a full-device reset.

iOS Simulator uses guarded simctl targets for install, launch, terminate, uninstall, privacy and URL commands. Install retains its fixed 300000 ms budget. App-container clearing resolves the selected container, checks containment, clears that exact container and publishes reset metadata through separate native leaves. Full simulator erase remains a separate workflow; container clearing adds no atomicity or rollback promise.

Physical iOS uses devicectl for install and launch. Stop obtains an owner-verified Appium session and sends one terminate-app request; the application owns its body and success interpretation. Physical uninstall, permission changes and URL opening retain their unsupported refusals. Physical app-data clearing has no provider case and falls through `undefined`; it does not introduce a new refusal or capability. Unknown targets retain fallthrough, while native owner, lease, process, session and filesystem authorities remain outside these applications.

Android core tests assert semantic effects, refusal precedence and failed observations. Existing MCP provider fixtures retain native argv, helper timeout, exit-zero launch diagnostic and public response coverage. Shared iOS app tests continue to exercise containment, publication and verified-session behavior. These portable fixtures do not certify real native hosts or physical devices.
