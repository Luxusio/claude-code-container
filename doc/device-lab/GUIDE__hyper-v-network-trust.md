# Hyper-V network allocation and Linux guest trust

The existing network exports compose `createHyperVNetworkTrust` for setup, broker lifecycle, journal cleanup and Linux guest callers. The application owns allocation admission, fabric ensure/reconciliation, release and cleanup sequencing, durable intent and confirmed-action checkpoints, retry decisions, and guest trust recovery. Existing adoption remains a compatibility helper; this extraction adds no adoption route or host configuration feature.

The factory has three required, finite port variants: state and trust-file policy, typed host observation/action policy, and complete network allocation policy. The network variant explicitly distinguishes typed fabric effects, legacy command compatibility and unavailable capability; owner-reference observations likewise distinguish available from unavailable. Missing authority is not replaced with an optional callback or a native client namespace. SDK contracts are type-only dependencies. The two named pure planners, `reconcileHyperVHostNetwork` and `planHyperVHostNetworkCleanup`, form a bounded shared policy kernel.

Native composition retains caller locks, owner records, guarded state and intent files, atomic file publication, revision hashing, executable resolution, command decoding and bounded diagnostics. `network-adapter.ts` binds individual typed observations and actions, exact-name VM inventory and the scoped administrator session. Native switch/NAT identity checks and elevation authentication remain authoritative before destructive effects. The application orchestrates these leaves; it cannot bypass their identity or file guards.

Allocation ensures or reconciles fabric before publishing a collision-free address and MAC. Existing allocations are retained, and reuse requires matching owner, device and incarnation. Intent is durable before acquisition; confirmed mutations checkpoint their observed identity so interrupted ensure and cleanup can resume. Refused elevation, uncertain mutation responses, receipt conflicts and expired deadlines retain truthful failure or recovery evidence rather than publishing usable success. Orphan reconciliation requires readable owner records and qualified exact-incarnation VM absence; foreign metadata, uncertain identity and failed observations retain allocations.

Release respects incarnation conflicts and current state revisions. Explicit preservation can commit allocation removal while retaining managed fabric without destructive elevation. Final destructive release keeps the allocation until cleanup is confirmed. Deferred cleanup records confirmed removals against the matching revision; successors and foreign allocations are retained. Host effects and file publication can fail independently, so a failed result may follow partial native changes. These caller-locked read/compare/write workflows add no transaction, stronger generation guarantee, rollback or absence proof.

Linux guest trust requires the committed owner/device allocation and address plus a canonical single Ed25519 identity. Guarded `known_hosts` data supports repair of the derived public-key file, followed by the caller's guarded owner fingerprint publication. Interrupted fingerprint publication remains recoverable from durable trust data. Invalid identity, allocation mismatch or refused publication does not become trusted success. Native path guards, key decoding and fingerprint hashing remain outside the application.

Ordinary allocation, adapter and broker tests cover current ownership, checkpoints, successors, deadlines and trust outcomes; core and consumed type tests cover policy and required capabilities. Their current execution, genuine build/package checks, integration review and local delivery remain pending acceptance work. This source Guide grants no five-operation credit, formal close or real Windows Hyper-V/UAC/guest certification.
