# Broker Hyper-V snapshots

One broker snapshot application owns list, create, restore, delete, and journal repair for Windows VMs and Hyper-V Linux VMs. Authenticated device-tool routing, owner queues, target lookup, and device-operation locks remain in the broker. Snapshot-specific admission, transaction decisions, result classification, and Linux restore readiness live inward.

Native peers retain checkpoint ownership checks, VM identity and terminal disk-chain observation, guarded journal files, PowerShell sessions, SSH commands, and atomic owner-state mutation. The application consumes explicit structural facts and captured native capabilities, never an executable, command recipe, native client or normalized broker options. Native execution crosses inward as `{ok,receipt?}`. Status supplies an already decoded VM observation; SSH supplies a readiness boolean through the existing Linux readiness decoder. The application does not parse native status, stdout, stderr or readiness markers. Diagnostics are derived outward from the receipt and an optional typed-error override, which retains precedence over a stale receipt error. Missing receipts are projected outward to the historical execution fields, never the semantic wrapper. Construction does not start providers. List, mutation and repair outcomes are semantic; native composition renders public HTTP responses and redacts diagnostic evidence. Lifecycle preflight consumes repair results directly.

List compares owner-tracked snapshots with live inventory and performs at most two bounded resamples inside one deadline. Compatibility exports use the same inward comparison and settling policy. Missing, untracked, or inconsistent snapshots remain conflicts; read failure is not empty success.

The broker captures one local monotonic allowance before waiting for device-operation locks. List, create, delete and restore receive 45, 75, 120 and 240 seconds respectively. Mutations share one additional 30-second cleanup reserve measured from that operation deadline. Repair, preflight, retries, native primitives, confirmation, Linux SSH readiness and publication consume the captured operation allowance; no phase renews it. Every transported timeout is a positive integral remaining duration. The MCP RPC defaults include cleanup plus a 15-second return margin, and the real-test client retains its additional 30-second margin. Explicit outer timeout overrides remain caller-owned. See [the finite budget requirement](REQ__hyper-v-monotonic-operation-budgets.md).

Create stages its journal before mutation and records a trustworthy returned checkpoint ID before confirmation. Unconfirmed or conflicting create evidence remains journaled for exact reconciliation. On a publication conflict, compensation targets only that newly created ID and expected provider name, and reports whether deletion was confirmed. Restore and delete do not invent rollback effects.

Restore requires destructive confirmation. Windows restores remain stopped; Linux restores start through the existing native peer and must become SSH-ready before publication. Successful native reads and readiness cannot authorize publication after expiry. Genuine failed execution and native rejection remain primary even when they complete late or bounded cleanup expires. Snapshot publication compares the complete captured owner record, validates the replacement and checks the deadline immediately before writing under the native mutation lock. A changed record is preserved.

Repair is internal. Ordinary Hyper-V tool preflight, native snapshot failure recovery, non-create lifecycle preflight, and create preflight all reach the same application. Repair validates owner/incarnation, VM/disk, checkpoint policy, exact provider name, and candidate cardinality. An indeterminate restore requires the exact retry ID and retains its journal. The existing forced VM-delete exception may supersede an unreconcilable snapshot journal.

Repair merges its selected snapshot/runtime fields into the current device selected by ID; this is the existing repair contract, not the stronger full-record CAS used by actions. Standalone repair captures one 60-second allowance; a supplied lifecycle or snapshot parent takes precedence. Journal and native identity failures stay explicit. Exact-ID recording and clearing qualify the captured target and whole journal, including operationId, under the existing repository lock. Late mutation completion may still record trustworthy exact-ID evidence. Clearing checks its deadline at the removal boundary and preserves replaced journals. When state publication succeeds but clearing expires, the state remains applied and its recovery journal remains present; the response reports the deadline failure. Selected typed snapshot deadline errors use the established HTTP 504 response.

Exported native snapshot helpers retain Unix deadline compatibility by capturing the Unix remainder once at entry and counting down locally. Their confirmation callback still receives Unix time. An internal remaining-duration callback takes precedence and cannot renew the captured allowance. A fired timer alone does not replace a genuine native failure; only the helper's own cancellation outcome becomes unconfirmed. Secret redaction and native session fallback rules remain in their existing outward peers.

Verification combines ordinary policy and consumed type tests with the existing Windows/Linux authenticated broker, journal, status, and typed snapshot fixtures. Emit workspace packages, assemble their runtime, emit Root, then reassemble before checking consumers that resolve generated `#device-lab` and `#hyper-v` imports. Run focused Vitest directly when a bounded verification plan excludes the repository test wrapper's automatic full build. Confirm the actual one-shot, session and safe fallback request durations respect the ten-second create-confirmation cap. Portable fixtures do not certify a real Windows host or live VM/checkpoint effects. Independent review, coordinated QA, a genuine build, and local delivery are required before acceptance.
