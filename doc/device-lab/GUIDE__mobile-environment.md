# Mobile environment and device clipboard

`createAndroidEnvironment` and `createIosEnvironment` expose synchronous `request(name, args)` methods for location, battery, network, airplane mode and device clipboard operations. The shared domain supplies admission and ordered semantic settings. Required variant-specific ports accept opaque targets and return finite success/failure observations with diagnostic receipts. Application outcomes describe completed operations, refusals, failed commands and missing prerequisites; the existing native backends encode ADB/simctl commands, interpret process status and render public results inside the existing outer operation locks.

Android emulator bindings provide guarded target selection, location, one battery setting, each of the three airplane steps, one radio setting and clipboard read/write. Each effect performs one command; fallback and partial-result decisions stay in the application. Physical Android requires plain owned-device lookup for unsupported environment requests and guarded target selection plus clipboard read/write for supported requests. Supported physical clipboard selection retains native lease checks. Serial qualification, prerequisite checks and command execution remain native authority; neither executable paths nor serials appear in the inward target contract.

For emulator network changes, at least one of `airplaneMode`, `wifi` or `data` must be supplied and every supplied value must be boolean; this admission occurs before target lookup. Battery and standalone airplane requests select the target first. Battery commands run in level, status, charging order and stop at the first failure. An empty battery request is refused after target selection. A failed battery command retains its command failure; it does not invent an `applied` result.

Airplane mode first attempts the modern connectivity command. Failure falls back to the global setting followed by the broadcast. A setting failure prevents the broadcast; a broadcast failure reports the already-applied setting. Network applies airplane mode before Wi-Fi and data. A failed radio command reports the ordered subset already applied, without rolling it back. These partial outcomes do not promise an atomic network update.

Android location requires an emulator serial or port, sends longitude before latitude and appends altitude only when supplied. Its success reports `adb-emulator`, command streams and status. Android clipboard write preserves `String(text)` and read preserves stdout bytes, including newlines. Both retain ADB status and provider fields. These are device clipboard operations, separate from host GUI/X11 clipboard synchronization.

The iOS Simulator variant requires owned-device lookup, native target selection, location and clipboard read/write. Native target selection performs discovery and exact owned-UDID resolution before returning an opaque handle, a refusal or missing prerequisite names. Location uses the latitude/longitude simctl form; clipboard write sends `String(text)` through stdin, preserving UTF-8 and newline bytes. Native presentation makes location and clipboard-write success include streams and `simctl` but omit status; clipboard-read includes stdout text, stderr and status. Native command failures remain failures rather than success projections.

Simulator battery, network and airplane requests use only owned-device lookup before their unsupported refusal; they do not discover tools. Physical iOS uses only owned-device lookup and retains unsupported refusals for all six operations, including clipboard. Unknown devices fall through `undefined`. No physical capability is inferred from Simulator or emulator support.

The accepted public request/Appium peer remains separate and unchanged. Its supported environment recipes differ from the native Android fallback sequence, and an Appium clipboard route does not make direct physical-iOS clipboard supported. Owner, lease, session, prerequisite and UDID authorities remain native or in their existing peers; this seam adds no hardware acceptance claim.

Core tests use semantic effects to check admission, sequencing, partial application and clipboard bytes. Existing MCP provider fixtures check the actual native recipes and public projections, including their differing status and failure-field omissions. Portable fixture results do not establish native host or physical-device acceptance.
