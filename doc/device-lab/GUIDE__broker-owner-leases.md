# Broker owner registration and physical leases

`createBrokerOwnerApplication` owns registration eligibility, equivalent locked reuse, canonical mount/profile resolution, and secret reuse or repair. Public registration/secret exports and the bounded HTTP resolve route use this same application. Canonical identity derivation remains shared with the existing owner identity module.

Required native capabilities retain guarded descriptor reads, directory checks and modes, scoped mutation locks, bounded randomness, and atomic file publication. Invalid auth material is quarantined before replacement. Successful publication permits identity- and ownership-checked cleanup of a non-directory quarantine entry; failed publication retains that evidence and propagates the primary publication error. A cleanup refusal does not prove the entry disappeared. This is not automatic restoration of invalid credentials.

`createBrokerPhysicalLeasesApplication` owns claim conflict and expiry decisions, locked rereads, heartbeat refresh, exact owner/device/claim admission, release, and incremental prune. It reuses the existing lease date and bounded scan/list applications. Native file guards and per-hardware mutation locks remain at the boundary. Shared cleanup callers use the same release and existing lease-restoration policy; restoration refuses an occupied destination.

The broker lease application also owns one instance-scoped managed-renewal registry. Attachment and successful release restoration activate renewal; ordinary claim and heartbeat RPCs do not. The composite owner/backend/hardware/device key selects replacement and cancellation. Renewal uses the existing one-hour default TTL and TTL/3 interval, with a ten-second floor and five-minute cap. Native leaves only allocate, clear and unref concrete timer handles. A non-200 renewal cancels its timer; a thrown native refresh retains the existing callback exception behavior. Broker server close delegates to stop-all. Prune itself does not cancel timers; their next refused refresh does.

Heartbeat reports `pruned: false` if expired-record removal fails. Prune returns only successful removals, preserving partial progress. Release cancels the owned heartbeat only after removal succeeds. Locking and guarded reads retain their existing guarantees; the extraction adds no claim that failed removal means absence, and no stronger generation or atomic compare-and-delete guarantee.

Ordinary factory/type tests and real authenticated HTTP/native-filesystem tests cover these boundaries. Static source readiness is not runtime acceptance, and portable test evidence does not certify native Windows filesystems or installed physical devices. Independent review and the shared genuine QA lane establish acceptance.

The direct Android/iOS provider lease store now composes a separate `createPhysicalLeases` application. It owns direct claim/reuse, TTL and expiry, heartbeat, prune, exact release, residue admission and owner-state mutation compensation. This keeps the existing direct lease schema and outcomes distinct from broker leases. Pure helpers consume explicit time facts; native leaves provide timestamps and ISO formatting, current owner identity, entropy and timer handles. One facade-scoped application owns managed heartbeat lifetimes; owner/home resolution remains lazy in native calls.

The native transaction scope holds the hardware lock before the aggregate lock and supplies the validated authoritative lease and aggregate snapshot plus individual guarded write/removal leaves. The application checks the remaining observation budget after those reads. It publishes a changed aggregate before a changed authoritative lease; authoritative publication/removal failure restores only a previously changed aggregate. A failed restore raises the existing combined aggregate rollback error. Heartbeat updates aggregate metadata only when that aggregate tracks the same lease identity, preserving standalone authoritative leases and foreign successors.

Direct release admits exact owner/device/claim/nonce matches. Residue removal requires one exact aggregate entry and retains its current absent-lock, expiry and authoritative-lock conflict checks. Release with owner-state mutation keeps rejected mutations uncommitted and invokes the supplied synchronous rollback only if lease publication fails; rollback failure retains the combined error. Managed heartbeat stops only after a successful release or a failed refresh. These rules add no schema, stronger atomicity guarantee or implicit foreign cleanup.

Native directory chains, bounded readers and validators, hardware/aggregate mutation locks, atomic writes, unlink rules and timer allocation/clearing remain authoritative outside the application. The ordinary whole `physical-lease-store.test.ts` suite and actual checked native constructor/required-port consumers qualify this direct binding after current strict checks, genuine build and shipping tests. Source extraction alone grants no whole lease operation, storage, native host or Goal completion credit.
