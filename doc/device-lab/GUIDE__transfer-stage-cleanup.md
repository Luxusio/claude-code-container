# Transfer stage cleanup

Local transfer stages belong to the operation that allocated or restored their fenced handle. Cleanup uses that handle once. A successful cleanup retains the original result or thrown value unchanged. A failed cleanup retains both the original result or tagged thrown value and the exact cleanup error; it never retries the transfer, commit, state transition or removal.

The native `cleanup():void` and application `dispose*():undefined` signatures stay unchanged. The shared filesystem helper exposes removal exceptions instead of swallowing them. Failed input staging first settles its ordinary failed staging result, then attempts cleanup once outside the copy/validation catch. If that cleanup also throws, a fixed-message `AggregateError` retains the failed staging result as `cause` and first error, and the removal exception as its second error. Validated discard returns its existing finite failure shape when removal fails. Existing path, prefix, descriptor and destination fences remain authoritative.

Android and iOS control applications distinguish ordinary results from `{kind:'cleanup-failure',primary,error}`. `primary` is the exact ordinary result or `{kind:'thrown',error}`; falsy thrown values remain distinct from successful work. Their ordinary result aliases are `AndroidControlResult` and `IosControlResult`. Neither application imports native file or MCP types. Admission order, copy/commit gates, owned handles and disposal signatures stay unchanged.

Direct recording similarly exposes `RecordingResult` and a cleanup failure with `primary`, `error` and `facts`. Facts contain only positively observed `outputPublished:true` and `recordingStateCleared:true`. Output publication is recorded immediately after a successful commit, before a later generation guard or clear can refuse or throw. Cleanup failure must retain these facts even when recording finalization itself did not complete. Successful start transfers a persistent stage's lifetime to the recorder; it is not disposed at return. Persistent simulator stages remain available after commit/state failure. Disposable finalization stages are finalized on the existing failure paths and unexpected execution throws. This change does not prove settlement of a recorder whose startup or initial metadata publication throws.

Native presenters use the outward `renderStageCleanupFailure(failure,jsonResult)` helper from `adapters/stage-cleanup-result.mjs`. Its required failure fields are `error` (the public code), `primary`, and `cleanupError`; optional `result` contains confirmed completion/publication facts. A thrown primary is `{kind:'thrown',error}`. An ordinary primary is `{kind:'returned',outcome:<ordinary kind>,result:<existing public response>}`. The helper renders the existing bounded MCP envelope with `isError:true`, the ordinary public result or bounded thrown errno as `cause`, and failed local cleanup. Only a guarded own data errno matching `/^E[A-Z0-9_]{1,31}$/` is exposed from raw errors. Messages, stacks, staging paths and arbitrary exception properties remain internal.

Public cleanup codes are `android-transfer-cleanup-failed`, `ios-transfer-cleanup-failed` and `recording-stage-cleanup-failed`. Completed transfer primaries retain a separate `{kind:'completed',completed:true}` marker. Recording result facts do not claim recording completion unless its ordinary primary was successful. The existing desktop export and `desktop-transfer-cleanup-failed` response remain compatible by delegating to this helper. Ordinary success responses do not change.

Behavioral checks cover actual filesystem staging with controlled removal faults, failed staging plus failed cleanup, honest discard, primary/cleanup identity, same-handle single disposal, publication before generation refusal, and persistent-stage retention. The native filesystem failure regression must fail against the unchanged helper before Source is released. Existing Windows/macOS/Android/iOS provider fixtures and required compiler/build checks qualify the combined candidate. Portable faults do not certify actual macOS reclamation or Darwin Tart process cleanup.
