# Shared Device Lab request policy

The MCP server registers the public tools and stdio transport, then delegates each call to one `createDeviceRequest` application. The application selects the operation, admits public arguments, applies destructive policy, chooses a direct or broker route, converts mobile and broker requests, and presents the result. All aliases share this path.

Explicit broker routing, implicit broker inventory, direct opt-out, current-display targets, backend ambiguity and backend mismatch remain distinct decisions. Explicit broker intent is selected before local provider work, including when implicit routing is disabled. A local Linux target must not collide with another local backend or an available broker target before mutation; uncertain broker inventory refuses the operation. Provider handlers are tried in their existing order after route admission. Recursive inventory, file-list execution and start-readiness probes call the same application rather than a second dispatcher. Screenshot cropping and flow execution reuse the existing peer operations.

`DeviceRequestPorts` describes the individual broker, provider, inventory, clock and encoding capabilities required by the application. The JS implementation consumes this declaration through JSDoc; shared QA must check the implementation and declaration together with strict `checkJs` and `skipLibCheck: false`. Broker authentication, HTTP, native process and storage mechanics remain in their existing outward modules. The application receives no native namespace or legacy dispatcher callback.

Ordinary application tests and current MCP fixtures cover route precedence, opt-out, denial before effects, actionable input and unsupported errors, output shape, readiness and file listing. These checks do not certify native hosts or each provider operation. This extraction completes the shared request responsibility; inventory, provider execution and other operation obligations require their own evidence.
