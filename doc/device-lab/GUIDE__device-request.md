# Shared Device Lab request policy

The MCP server registers the public tools and stdio transport, then delegates each call to one `createDeviceRequest` application. The application selects the operation, admits public arguments, applies destructive policy, chooses a direct or broker route and converts mobile and broker requests. Required native presentation capabilities return an opaque result. All aliases share this path.

Explicit broker routing, implicit broker inventory, direct opt-out, current-display targets, backend ambiguity and backend mismatch remain distinct decisions. Explicit broker intent is selected before local provider work, including when implicit routing is disabled. A local Linux target must not collide with another local backend or an available broker target before mutation; uncertain broker inventory refuses the operation. Provider handlers are tried in their existing order after route admission. Recursive inventory, file-list execution and start-readiness probes call the same application rather than a second dispatcher. Screenshot cropping and flow execution reuse the existing peer operations.

Backend discovery produces a semantic catalog before presentation. Successful direct and broker catalogs are filtered without mutating their observations; failed discovery keeps its diagnostic catalogs unfiltered. The application does not parse MCP JSON to select backend facts.

`DeviceRequestPorts<Result>` describes the individual broker, provider, inventory, clock, encoding and presentation capabilities required by the application. Flow and provider capabilities use the same opaque result without a default MCP shape. The JS implementation consumes the declaration through JSDoc; shared QA checks the implementation and declaration together with strict `checkJs` and `skipLibCheck: false`.

The outward `device-request-presenter.mjs` owns native MCP types and the synchronous broker-result and image presenters. A successful broker native envelope takes precedence, including an error envelope. Otherwise the presenter uses the fallback facts selected by the application. Recording fallback flattening and file-list composition remain application decisions. The server binds the actual presenters; the flow adapter decodes and attaches native content. Broker authentication, HTTP, process and storage mechanics remain in their existing outward modules. The application receives no native namespace or legacy dispatcher callback.

Ordinary application tests use a result without MCP fields and consume the actual presenter bodies under the normal strict compiler. Valid and missing Appium screenshot data are exercised through the application's private `mobile_screenshot` dispatch; public `screenshot` separately exercises the native broker device-tool envelope. Current MCP and flow fixtures qualify server/adapter composition, route precedence, opt-out, denial before effects, output, readiness and file listing. They do not strictly certify every unrelated legacy native helper or real host. Inventory, provider execution and the remaining original architecture obligations require their own evidence.
