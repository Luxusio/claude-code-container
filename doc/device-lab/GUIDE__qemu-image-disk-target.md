# QEMU image, disk and passive target operations

`createQemuImageDiskTargetApplication` owns image enumeration, disk materialization decisions and passive target selection. Domain functions infer image formats, bound timeouts, build overlay arguments and project lab metadata. The Linux VM facade supplies finite synchronous ports for owner context, guarded storage observations, provider status, command execution, time and publication. Native ownership, symlink, path and process guards remain at the effect boundary.

Image listing returns readable owner metadata without creating a missing images directory. Materialization validates the lab and disk, rejects a running lab, and reuses an existing disk unless `force === true`. Dry runs plan without creating or publishing storage. Execution validates the provider before running QEMU image creation; a publication failure can leave the created overlay. Passive target listing projects stored runtime/readiness metadata without probing processes or guests.

Image listing is exported as `listImages`, reached through `handleLinuxVmManagementTool` and exposed by MCP `list_images`. Disk materialization and target listing are package exports reached through `handleLinuxVmTool`; the public MCP catalog omits `device_disk_materialize` and `device_target_list`.
