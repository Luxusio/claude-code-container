# Broker owner repository

The broker composes `createBrokerOwnerRepository` with required synchronous ports for owner-list reads, the owner mutation lock, writable validation, atomic publication, deep equality and timestamps. The application owns selection, identity conflicts, generation matching and publication decisions. The domain admits unique IDs and simple or compound claim selectors, while existing physical, recording, Appium and cleanup predicates retain their shared rules.

Ordinary mutation always validates and publishes, including unchanged lists. Lifecycle transitions select the first matching device and compare the complete record; missing or mismatched records do not publish. Snapshot, recording and Appium transitions retain their distinct results and always-publishing mutation semantics even when unmatched. Snapshot recovery merges the selected device rather than replacing an independently changed record. Physical reattachment requires exactly one matching detached device. Appium replacement timestamps take precedence over the native timestamp leaf.

The same application owns selected device removal and update, cleanup replay publication and Windows configuration claim compensation. Native callers retain transport, authentication and operation-specific side effects. Native owner paths, bounded content readers, file identity and parent-directory guards, locks and atomic writers remain outside the application; neither record projections nor timestamps grant filesystem authority.

Ordinary repository core and required-port tests accompany existing broker command, attachment, lifecycle, snapshot and Appium suites. Verification requires the current architecture graph, strict native consumers, genuine build, whole affected suites and actual package/CLI smoke. Static authoring does not prove those checks or native host behavior. This seam is one owner-repository binding; broader storage publication and locking work remains separate.
