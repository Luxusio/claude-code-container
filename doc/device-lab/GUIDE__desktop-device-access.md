# Desktop device access

`createDesktopDeviceAccess` owns Windows Sandbox and macOS VM status, exec, screenshot and accessibility result policy through required variant-specific native ports. `handle(name, args)` returns asynchronous outcomes; unknown targets fall through. Existing public MCP and authenticated broker callers, operation locks and macOS recovery admission continue to reach the native facades. This seam adds no desktop capability or lifecycle policy.

Windows requests use the existing guarded helper channel. The application chooses an exec, screenshot or bounded accessibility request and interprets the correlated native response. Native code retains helper identity, request correlation and output-path verification. Screenshot output must resolve to the verified helper path and pass the native file reader’s checks before image publication. Helper failure, unsafe or missing output and invalid image remain distinct refusals. Accessibility depth and node limits are pure domain decisions.

macOS status uses native discovery and public-device projection. Exec selects the guarded SSH bridge and reports the native streams and status as JSON, including nonzero status such as 7; it does not turn every nonzero exec into a separate refusal. Accessibility uses the existing native helper and parser, with bounded arguments and current provider/result presentation. Keys, SSH/SCP invocation, remote scripts, identity checks and native command limits remain outward mechanisms.

macOS screenshot policy allocates the native stage, captures remotely, copies locally and reads the guarded image. Capture or copy failure remains a command failure. The existing `finally` calls remote cleanup before local stage disposal. A returned nonzero cleanup status does not replace the selected result; a thrown remote cleanup prevents the later local-disposal call and propagates. This documents the actual partial cleanup behavior, not an unconditional rescue guarantee or stronger transaction.

`createDisplayDeviceAccess` serves the current X11 display. Its synchronous `current()` constructs the target from finite owner, display and availability facts through the domain and native presentation. Screenshot handling allocates a native stage, invokes one capture, reads the guarded result and disposes the stage in `finally`. Native display discovery, capture commands, filesystem handles and file validation remain authoritative. Display target projection grants no new host access.

Required ports expose these concrete leaves rather than complete old access workflows. Existing control/transfer, recording, lifecycle and public routing peers remain separate. The Guide describes the seam and current outcomes; compiler, runtime, shipping and native hardware acceptance are separate verification work.
