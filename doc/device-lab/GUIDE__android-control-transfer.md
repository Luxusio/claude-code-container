# Android control and transfer

Both Android adapters compose `createAndroidControlTransfer`. The shared application owns the selected tap, double tap, long press, swipe, drag, text, key, navigation, orientation and upload/download workflows. The domain builds action arguments and result data, preserving current defaults and the different emulator versus physical navigation payloads. The application refuses a failed first tap before issuing the second, and reports transfer success only after the required native steps succeed.

Required typed ports expose target observation, target-bound ADB execution, bounded transfer commands, guest-path validation and owned local stage allocation/commit/disposal. The adapters retain current owner and physical-lease guards, serial binding, command profiles and guarded file authority. Output stages use the existing atomic publication helper. Disposal attempts retain the original result or exception together with a cleanup failure, following the [shared cleanup contract](GUIDE__transfer-stage-cleanup.md). The existing response presenters retain bounded diagnostics. Construction starts no provider.

Orientation resolves the current target before validating the requested value. Left selects landscape and right selects reverse-landscape. The application first disables accelerometer rotation, then sets the requested user rotation. A failed first command prevents the second; a failed second command retains the first setting, with no rollback. Successful results expose only the second command's streams and status. These operations reuse the synchronous target-bound execution port.

Common DeviceRequest aliases and authenticated broker backend-child routing reach these same adapters. Lifecycle, observation, wireless, recording, waits, screenshots and other Android settings remain separate peers. This Android cohort does not complete the corresponding operations across other providers or Appium bindings.

Current ordinary core/type and public emulator/physical suites are the verification surfaces. Independent review and shared strict/build/runtime QA are required before delivery. Static development alone does not prove runtime behavior; actual host/device ADB certification remains unrun unless separately authorized.
