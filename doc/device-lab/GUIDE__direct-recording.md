# Direct provider recording

`adapters/direct-recording.mjs#createDirectRecording` constructs actual finite native bindings and the shared application. Its result exposes `request(name, args)` for start/status/stop and `exited(deviceId, recording)` for guarded recorder exit observations. Native facades render semantic `success.value`, `failure.message`, `native.value`, or missing outcomes. Existing owner-operation and physical lease guards stay around the provider entrypoints. Public Android time-limit guards call domain `recordingInputError` before their native lock when the current selected-backend guard applies.

The application owns recording admission/defaults, semantic recorder selection, active/pending decisions, generation publication and compensation, finalization and artifact-retention policy. It reuses the accepted runtime-generation application/domain. Native mechanisms select owned devices and concrete executable/target facts, perform individual bounded commands and correlated helper requests, and retain filesystem/identity authority. The checked producer binds entropy/clocks, detached child spawn/events/startup observations, identity/signaling/PID waits and fenced stage effects; it imports no whole backend.

Android emulator rejects any existing recording on start. Physical Android resolves its selected ADB target and reconciles recording state first. Both retain screenrecord arguments, the 180-second default, existing selected-target fallback, 300000ms transfer bounds and staged finalization. [Android settlement](REQ__direct-android-recording-settlement.md) gates every public finalize/retry, including inactive records: matching host identity requires observed cessation and fresh guest absence; valid mismatch permits recovery only with guest absence and no local signal. Unknown/malformed identity, running/unavailable guest state, expiry or captured target/generation/lease conflict preserves recovery evidence. One monotonic 3000ms allowance bounds settlement calls; signal acknowledgement is insufficient. Failed transfer preserves pending recording; final CAS refusal preserves successor and remote artifact. Remote removal follows successful clear; interpreting its outcome remains separate work.

Simulator start rejects existing recording and records to a persistent `.recording-stage-` payload. Stop refuses an unsafe owned signal, then uses the exact generation's pending claim. Persistent-stage retry restores its fenced stage; legacy records populate a separate temporary stage. Failed population leaves the legacy source/pending metadata; failed commit or final CAS retains the persistent artifact, while disposable legacy stages follow the existing cleanup branches.

For a legacy Simulator recording without a persistent stage, pending `localPath` continues to identify its original recording source. A different requested output path belongs to that finalization attempt and is returned after successful publication; a failed attempt must not replace the pending source with that destination. Retrying population or publication therefore copies the original recording bytes even when the destination already contains a nonempty older file. Persistent-stage and other-provider claims retain their existing path handling.

The [shared cleanup contract](GUIDE__transfer-stage-cleanup.md) preserves the primary result or thrown value alongside a disposal failure. Confirmed output publication and state clearance remain visible even if a later guard or removal fails. Disposable finalization stages are cleaned on execution exceptions; persistent recovery stages retain their existing lifetime. Recorder startup/initial-publication process settlement remains a separate requirement.

macOS start rejects existing recording and resolves its SSH bridge/workspace before spawning screencapture. Only macOS catches a thrown initial metadata publication: it suppresses its allocated recorder's exit publication, sends SIGINT and waits1000ms, then SIGKILL and waits1000ms if necessary. Other start variants retain their existing exception boundaries. macOS stop retains the remote pkill fallback, existing PID-based3000ms wait, staged SCP copy and remote removal after final generation clear.

Sandbox uses helper sessions rather than local recorder PID authority. Status and start reconciliation can publish a completed archive and conditionally clear its exact generation. Helper start/stop/status retain5000/10000/1000ms defaults. Short truthy limits select500ms capture intervals; other limits select1000ms. A failed start CAS stops the newly allocated helper session. Stop failures retain metadata for retry; a failed final CAS reports successor conflict only when a recording remains in the returned record. Archive path/correlation and bounded copy fences stay native.

An OK Sandbox helper response without a recording no longer dereferences missing archive fields. Status reports missing or unsafe output and preserves the recording metadata for retry.

All process exit callbacks call `exited` with guarded generation transitions. A true child-exit callback can publish pending local evidence. Android finalization independently checks guest absence, so inactive metadata cannot bypass settlement; start/status add no guest polling. Generation checks preserve same-ID successors. The application never claims universal rollback or verified local exit from a remote fallback.

Native composition uses the discriminated `DirectRecordingNative` contract. Common inputs are guarded find/update, default local path and output-path validation. Process variants add recording-directory and concrete target resolution; Android/macOS add finite command effects, macOS adds workspace preparation. Sandbox adds individual helper request, verified archive path and bounded copy receipts. No complete start/finalize/reconcile callback or application-port bag is accepted.

Existing five-provider business journeys, macOS rollback/desktop-video suites and real authenticated default-child Sandbox/macOS journeys qualify the supported bindings. Small static contracts consume both actual factories; the strict architecture target checks real application and native producer bodies. Compiler/runtime/build/shipping and native-platform acceptance remain separate gates; this Guide grants no whole-operation or Goal certification.

Fixed ADB/simctl/SSH/SCP arguments and POSIX shell quoting live only in the checked native producer. The application invokes individual `spawnRecorder`, `fallbackStop`, `copyRecording`, and `removeRecording` effects with admitted target facts and semantic paths. It selects deadlines, defaults, effect order and generation transitions; copy returns `{ok,detail,output}`. The native producer classifies the existing
status0-only predicate, prepares failure detail and the finite public output
fragment; the application consumes only `ok`/`detail` for its decisions. The
opaque output preserves Android stdout/stderr/status and macOS stdout/stderr,
and is carried outward only after successful stage commit and generation clear.
Android settlement effects expose finite host/guest/signal facts. Other unchanged command effects retain their compatibility receipts. Native process result types and
command-output interpretation stay outside the application. Initial target admission and the `runCommand(command)` contract retain their behavior. Repeated Android validation carries the captured ADB target and optional remaining budget: native compositions reuse the admitted executable, derive current selected arguments from authoritative state, and pass that budget into existing exact physical lease heartbeat locks. Synchronous lock identity acquisition and stale-owner observations pass the live remainder into the existing native identity APIs in both bindings; expired results cannot populate the cache or authorize a claim. It does not repeat executable discovery inside settlement.
