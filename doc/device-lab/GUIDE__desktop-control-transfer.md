# Desktop control and transfer

`createDesktopControlTransfer` routes the existing X11, Windows Sandbox and macOS VM desktop actions through one application. The application owns input admission, platform defaults, owned-target selection, focus decisions and transfer publication. Its ports are named operations such as `activateWindow`, `key`, `cursorPosition` and `upload`; they return success/failure observations with opaque native evidence. Outcomes describe completion, refusal or native failure. The existing platform facade renders the public response.

The domain owns integer coordinate and drag-duration rules. Native key mappings belong to their platform facade: Windows encodes SendKeys expressions and literal text, while macOS resolves supported key codes and modifiers. The application asks the pure macOS `supportsKey` capability before executing a key action. It never builds xdotool arguments, helper requests or SSH/SCP commands, parses native stdout, or selects public provider/result fields.

X11 activation and readback are separate effects. The application skips readback after failed activation and compares the decoded active-window handle exactly with the admitted handle. Native leaves own the two bounded commands, window-list framing and cursor parsing. macOS focus reports whether the native helper verified the requested window; the application refuses unverified focus. Platform differences remain deliberate: X11 scroll defaults to three steps, Windows/macOS to one; Windows scrolling requires coordinates while macOS scrolling does not. Pointer and drag admission retain their existing bounds.

Windows transfer admission checks the guest path before the local path or upload allocation. The upload stage stays alive until the asynchronous request settles and is disposed in `finally`, including rejection or an unexpected exception. Download publication requires a successful helper request, verification of the helper-selected output path and a successful bounded copy. The native facade retains helper response ID/type checks, safe output selection, file/link/size fences, key/text encoding and full bounded cursor diagnostics. Unexpected exceptions continue to propagate after cleanup.

macOS transfer admission remains SSH prerequisites, guest path, local stage, transfer, then output commit. Failed transfers skip commit; successful downloads publish the committed local path. Every allocated stage is disposed in `finally`, including transfer/commit exceptions. Input and output use the same concrete stage type; the existing native staging and commit functions own path and file authority. SSH bridge and Windows target/workspace/upload handles retain their distinct roles.

Each facade owns concrete native evidence and public fallback behavior. Windows/macOS keep helper-supplied click/key/text/scroll values when present and their established defaults when absent. Empty or malformed macOS JSON retains those fallbacks; focus still requires explicit verification. Windows cursor timeout, ordinary failure and rejected-response diagnostics keep their existing disclosure limits. X11 native command failures and malformed window lists retain their public errors. Neighboring DesktopDeviceAccess, recording and lifecycle behavior remain separate.

Core tests verify policy, admission order, focus decisions, publication gates and allocation lifetimes using ordinary finite ports. Consumed type cases enforce required named capabilities, asynchronous Windows operations and synchronous X11/macOS operations, staging, commit and disposal. Existing provider/public tests verify command/helper bindings, output fallbacks, file contents and cleanup. Source expression, getter timing and function shape are not product contracts.

Controlled fake-provider and packaged-entry checks do not establish live Windows/macOS GUI behavior, SSH authentication or provider availability. This boundary work does not certify the entire architecture migration or arbitrary container-runtime portability.
