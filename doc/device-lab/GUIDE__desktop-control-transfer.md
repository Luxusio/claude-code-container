# Desktop control and transfer

`createDesktopControlTransfer` routes the existing X11, Windows Sandbox and macOS VM desktop actions through one application. The application owns input admission, platform defaults, owned-target selection, focus decisions and transfer publication. Its ports are named operations such as `activateWindow`, `key`, `cursorPosition` and `upload`; they return success/failure observations with opaque native evidence. Outcomes describe completion, refusal or native failure. The existing platform facade renders the public response.

The domain owns integer coordinate and drag-duration rules. Native key mappings belong to their platform facade: Windows encodes SendKeys expressions and literal text, while macOS resolves supported key codes and modifiers. X11 translates desktop aliases such as `Enter` to `Return`, including known components of modifier combinations, while preserving other native expressions. Its specific ignored-unknown-key diagnostic is failure even at exit zero; ordinary stderr remains evidence. The application asks the pure macOS `supportsKey` capability before executing a key action. It never builds xdotool arguments, helper requests or SSH/SCP commands, parses native stdout, or selects public provider/result fields.

X11 activation and readback are separate effects. Discovery advertises focus only after a bounded nonmutating native readback supplies a valid positive handle; a failed probe does not diagnose every possible WM or connection failure. The application skips readback after failed activation and compares the decoded active-window handle exactly with the admitted handle. Native leaves own the two bounded commands, window-list framing and cursor parsing. macOS focus reports whether the native helper verified the requested window; the application refuses unverified focus. Platform differences remain deliberate: X11 scroll defaults to three steps, Windows/macOS to one; Windows scrolling requires coordinates while macOS scrolling does not. Pointer and drag admission retain their existing bounds. The [current-display contract](REQ__x11-current-display-tool-contract.md) defines input, discovery and routing failure behavior.

Windows transfer admission checks the guest path before the local path or upload allocation. The upload stage stays alive until the asynchronous request settles and its captured handle is disposed exactly once, including rejection or an unexpected exception. Download publication requires a successful helper request, verification of the helper-selected output path and a successful bounded copy. The native facade retains helper response ID/type checks, safe output selection, file/link/size fences, key/text encoding and full bounded cursor diagnostics. A primary exception propagates unchanged when disposal succeeds.

macOS transfer admission remains SSH prerequisites, guest path, local stage, transfer, then output commit. Failed transfers skip commit; successful downloads publish the committed local path. Every allocated stage is disposed once, including transfer/commit exceptions. Input and output use the same concrete stage type; the existing native staging and commit functions own path and file authority. SSH bridge and Windows target/workspace/upload handles retain their distinct roles.

If a disposal port throws, the application retains both its error and the exact earlier completed, failed, refused or thrown primary observation. It does not retry the transfer, commit or disposal, recalculate the stage path, or erase evidence of a completed upload/publication. Native facades render this finite failed outcome before interpreting ordinary native evidence. The failure response keeps the existing MCP envelope and uses `desktop-transfer-cleanup-failed`; its cause contains the ordinary public result or identifies a thrown primary, and its cleanup describes failed local disposal. A completed primary also has a separate completed-result marker. Overall `isError:true` makes an ordered flow stop even when transfer itself completed. Ordinary success responses remain unchanged.

Raw primary and cleanup exceptions remain internal. Public cleanup diagnostics expose only a validated bounded Node errno when available, never exception messages, stack traces, private staging paths or arbitrary properties. The existing JSON response renderer bounds the diagnostic while retaining the completed-result marker.

Known ceiling: native macOS transfer stages currently suppress filesystem cleanup errors in the shared `transfer-file.mjs` helper, so this application cannot report an error that its port does not expose. Changing that shared policy requires its Android/iOS/other transfer callers to be assessed together; portable disposal-fault tests do not establish native macOS resource reclamation.

Each facade owns concrete native evidence and public fallback behavior. Windows keeps truthy helper-supplied click/key/text/scroll values and uses its established defaults otherwise. macOS key and text results describe the admitted input and native key specification; its click and scroll results keep truthy helper values or use the established input defaults. Empty or malformed macOS JSON retains click/scroll/cursor/window-list fallbacks; focus still requires explicit verification. Windows cursor timeout, ordinary failure and rejected-response diagnostics keep their existing disclosure limits. X11 native command failures and malformed window lists retain their public errors. Neighboring DesktopDeviceAccess, recording and lifecycle behavior remain separate.

Core tests verify policy, admission order, focus decisions, publication gates and allocation lifetimes using ordinary finite ports. Consumed type cases enforce required named capabilities, asynchronous Windows operations and synchronous X11/macOS operations, staging, commit and disposal. Existing provider/public tests verify command/helper bindings, output fallbacks, file contents and cleanup. Source expression, getter timing and function shape are not product contracts.

The Windows public MCP fixture must also exercise a completed upload with an exact-stage deletion failure. Its response must retain completion and cleanup failure together, while the failed deletion leaves the staged file available for owned test teardown.

Controlled fake-provider and packaged-entry checks do not establish live Windows/macOS GUI behavior, SSH authentication or provider availability. This boundary work does not certify the entire architecture migration or arbitrary container-runtime portability.
