# Direct macOS VM lifecycle

The direct macOS provider retains `handleMacosTool` as its public entry point. Its canonical single-device and clone-source operation locks, argument handling, raw native results, and public response format remain in place. `device_create`, `device_start`, `device_stop`, and `device_delete` now dispatch to `createMacosVmLifecycleApplication`.

The application owns lifecycle admission, stale-claim recovery, complete-record conditional publication, and compensation decisions. Metadata-only create preserves the existing owner identity, SSH policy, resource defaults, and duplicate handling. Create with `sourceImage` or `image` reaches the inward image-create policy: Tart selection, clone result handling, timed-out clone cleanup, managed-resource metadata, and claim exception/conflict rollback. The retained base-image-create caller uses this same policy. Base-image-clone and snapshot operations retain their existing behavior and share only the extracted lifecycle and clone helpers; they do not gain whole-operation credit.

Start preserves key validation, provider planning, headless selection, native launch and child `unref`, runtime publication/readback, boot/helper progression, and final lifecycle completion. A successor record can veto runtime or completion publication; the original guarded rollback reports whether the provider instance belongs to that successor. Stop retains provider-stop ordering, recording signaling and remote cleanup, recording wait, and conditional metadata clearing. Delete retains force-stop admission, managed snapshot/recovery/device resource ordering, publication after each partial removal, and final conditional record removal. Failed commands and already-completed effects keep their original diagnostics.

The domain module owns mutable, open record fact types and contains resource-reference and managed-resource predicates plus the original pure SSH/default-credential selection. Required ports name individual repository, provider-command, launch, recording, SSH, clock, and response capabilities. They carry mutable native records and the actual child handle rather than a PID substitute. The facade selects imported native callees lazily and invokes them bare; the child's `unref` retains its receiver. There is no default native capability or callback that executes a whole lifecycle.

Stale-claim parsing uses the required synchronous `parseLifecycleClaimedAt` native leaf. Its lazy getter captures `Date` and the parser before reading the claim timestamp, then invokes the captured parser with the original `Date` receiver after argument evaluation. A noncallable parser follows the original native property-call error without timestamp coercion; getter, argument and parser errors remain raw. Domain fact types do not import outward port declarations; neither domain nor application observes ambient `Date`.

Native authority stays in the existing owner repository/CAS, process-identity and runtime-generation guards, guarded SSH key/askpass/artifact operations, provider adapters, and canonical boot/helper readiness routines. The extraction does not strengthen full-record comparison into byte-identical ABA protection or imply that a selected PID alone proves process ownership. Native timeouts, polling, filesystem checks, secret handling, and cleanup constraints remain authoritative.

Independent tests consume the frozen whole original facade, its native witnesses, public namespace/default arities, ordered raw observations, and source/emitted contracts. Core, facade, and strict type cases cover the four workflows, reached image compensation, stale recovery, successor refusals, partial failures, and required synchronous/asynchronous leaves. Source preparation and static syntax checks are not executed QA. Actual source/emitted strict checks, controlled facade execution, and affected review are required before integration.

This guide covers the direct provider only. The separate broker-native implementation and authenticated public/broker bindings, both distribution forms, final full verification, and local delivery belong to the dependent iOS/macOS lifecycle integration task. Provider-only results establish no whole-operation or WBS credit. macOS start remains partial until that integration completes. Real macOS, Tart, VZ, UTM, hardware, and guest acceptance remain separately unverified by portable controlled-native fixtures.
