# Hyper-V create, start and reboot

Authenticated broker lifecycle requests compose `createHyperVCreateStartApplication` for owned Windows and Hyper-V Linux VM create/start/reboot. The application owns admission, image/profile selection, network acquisition, incarnation claims, journal progression, typed VM creation, compensation and create-residue recovery. Existing inward image, network and stop/delete peers remain connected. Dry runs are decided before resource, journal or provider mutation; this extraction introduces no public lifecycle feature.

Required finite ports expose individual guarded storage observations, conditional owner publication, journal operations, VHD preparation and inspection, VM configuration/power effects, credentials/media, guest probes and clocks/deadlines. The native adapters retain authenticated sessions, locks, OS and filesystem authority, exact VM/disk identity, command decoding and guarded process execution. Type-only Hyper-V SDK contracts describe data; application decisions do not confer native authority or receive a broad client namespace.

Typed creation owns step admission, receipt advancement and final definition qualification. A matching new-VM receipt is retained before later configuration failure; malformed or uncertain responses do not become trusted VM identity. Compensation uses confirmed effects, reserved cleanup time and native identity guards. Failed removal keeps retryable journal/residue evidence, and recovery preserves same-ID successors and unrelated resources. Cleanup and state publication can fail after partial native effects; no stronger transaction, rollback or absence guarantee is added.

Start and reboot own power sequencing, readiness interpretation and final conditional publication. `waitForBoot: false` retains its existing disposition. Windows readiness handles signed provisioning evidence, first-logon progress, bounded no-progress retries, secret scrub and media detachment verification. Linux readiness retains bootstrap SSH, fingerprint qualification and network finalization. Fatal or uncertain post-effect failures use bounded containment and truthful retry metadata, including reserved cleanup time after the main budget expires. Proven nonexecution remains distinct from a provider effect whose outcome is uncertain. Native owner/incarnation, VM identity and complete-record publication guards remain authoritative throughout.

The container-QEMU reboot binding reaches its accepted lifecycle application. It retains provider preflight, force and `startIfStopped` decisions: a failed stop prevents start, and a failed start reports the completed stop and actual failed start rather than successful reboot. This companion binding does not transfer QEMU native process or resource authority into Hyper-V policy.

Ordinary broker, typed creation, readiness and QEMU lifecycle tests cover public outcomes, compensation, successors and failure containment; consumed type tests cover required capabilities. Current independent reviews, strict compilation, runtime tests, genuine build/package checks and local delivery remain acceptance work. No Windows Hyper-V, guest or QEMU host certification, operation credit or formal close is claimed by this source Guide.
