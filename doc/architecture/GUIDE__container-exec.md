# Container command execution

`src/application/container-exec.ts` owns the complete command session: acquire ownership before starting a container, select guarded replacement, coordinate setup, prepare the selected tool and environment, launch the command, and dispose its owned environment artifact and session. It returns a status. The private `exec` wrapper in `src/index.ts` binds the application and exits with that status for all existing CLI dispatch routes.

`src/ports/container-exec.ts` names semantic observations, individual effects and existing operation delegates. The application builds the ordered guest environment from host facts, retaining defaults, duplicate entries and explicit override priority. Command preparation is an opaque handle; executable, native arguments, streams and the owned environment-file path stay in composition. Lifecycle, setup, family and Codex configuration locks remain separate. The application keeps the final pinned container ID after a setup restart. Reused containers skip heavy installation but still regenerate MCP configuration and pass final readiness checks.

`src/composition/container-exec.ts` binds existing container, session, worktree, clipboard, Codex and command authorities. It encodes mise, bridge, command and debug requests and renders finite reports and failures. Codex's native facade classifies daemon probes and presents fallback arguments; its application decides whether to initialize or use the qualified fallback. The CLI supplies its asset directory and trusted filename without an inward import of the CLI. Native ownership, process, file and container identity guards remain in their existing modules.

Launch uses an ordered semantic plan. The existing Docker facade and runtime helpers serialize native flags, mounts, Compose labels and runtime-specific settings. Creation receives an opaque preparation and a normalized created-ID observation; source assertions, identity verification and exact-ID compensation remain application decisions.

Early startup failures continue through `runCli` cleanup. Preparation creation stays outside the local command try/finally. Once prepared, command completion or failure restores Codex access under its lock, disposes the artifact and cleans up the session. Interactive Codex preparation also runs without a terminal; terminal-dependent launch and recovery are selected afterward. A denied preparation returns its status without launching the user command. Optional cleanup diagnostics do not replace the command outcome.

Current tests cover these outcomes with ordinary fake ports and public CLI/native regressions. There are no archived implementation oracles, VM membranes or getter-order requirements. Fixture success does not certify live Docker/Podman interaction or native macOS/Windows hosts; those require actual host runs.
