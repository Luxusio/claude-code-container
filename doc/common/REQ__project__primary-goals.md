# Primary Goals

Run Claude Code in isolated containers with:

1. **Per-project isolation** — containers named by path hash, each project gets its own environment
2. **Runtime-agnostic container execution** — works with Docker or Podman; auto-detect with Podman preferred, override via `--runtime` / `CCC_RUNTIME`. First-class support for rootless Podman on Linux and podman machine on macOS/Windows (added 2026-04-17)
3. **Host environment forwarding** — auto-forward env vars, SSH agent, locale, timezone
4. **Session lifecycle management** — lock files track sessions, auto-stop the container when the last joined session exits, and never automatically replace a running project container, including when the current CLI owns the only session lock. Once a CLI invocation's initial container-status snapshot observes an existing project container running, that invocation must retain the observation as a destructive-operation fence: later stopped, unavailable, or contract-drift observations in the same invocation may defer or abort, but must not authorize removing or recreating that container. Every automatic replacement path must first prove the container is stopped under the shared lifecycle lock before observing or pruning session liveness, then revalidate process identity before removal; unknown, timed-out, access-denied, and failed runtime probes fail closed. Replacement removes an already-stopped container without first issuing `stop`, so a concurrent external start aborts removal. V2 session locks use OS process start-token observation as the primary non-destructive liveness authority: only an explicit process-missing result or token mismatch classifies a stale lock, while empty, malformed, unavailable, timed-out, access-denied, and failed observations preserve it. Automatic last-session shutdown is stricter: every foreign lock filename is an ownership claim and blocks cleanup without PID or start-token inference, so Windows observation errors cannot authorize termination of another session. If start-token observation is unavailable during session creation, CCC must remain joinable by writing a conservative legacy PID lock instead of rejecting the session. Legacy PID-only locks are stale only when an OS observation explicitly proves the PID missing: `ESRCH` on non-Windows, or `MISSING` from the primary Windows probe or a verified System32 process enumeration; all uncertain probe failures preserve ownership. A lock directory that disappears or becomes unreadable after initialization must fail closed rather than represent an empty session set. Session cleanup and the clipboard watchdog share one lock parser and liveness implementation. Session lifecycle code retains lock-deletion authority under the owning container lifecycle lock; the global clipboard watchdog may only aggregate lock liveness without mutation and shuts down the singleton server after its no-session grace period. Closing one of multiple live sessions must never stop their shared container, including when Windows PID signal probing would return a false negative. Immutable mount/image contract updates are deferred until the container has stopped. A running CCC-managed container with the exact normalized project identity label and expected writable project mount destination remains joinable while missing additive credential, Git, VM, or device-broker mounts and non-authority environment differences are deferred. The project ID, container name, session-lock prefix, and `/project/<project-id>` working directory derive from the lexical absolute project path using the stable legacy algorithm and must not change across CCC upgrades because of filesystem canonicalization. Canonical Windows filesystem identity is used only to validate source equivalence and ownership; it must never replace the durable logical project identity. The project source must match the canonical host path or a recognized equivalent Windows/Docker Desktop representation. Existing non-project bind mounts must retain their expected source, type, and access, named volumes must retain their expected source, and obsolete authority-bearing mounts must be absent; credential, broker-auth, SSH, Git, and configured extra-mount substitution fail closed. Live bind-identity marker checks must wait for the pinned container to become exec-ready with a short bounded retry, then still require the exact marker proof and revalidate the host source identity; readiness never substitutes for mount identity. Post-handoff liveness checks must query an exact pinned hexadecimal container ID as an ID rather than as a container name, so a newly created running container cannot be misclassified as stopped and sent through a second start/contract-validation path. Setup diagnostics must report only the observed unavailable state and must not claim a concurrent session without ownership evidence. The container-manager socket must remain a writable bind at `/var/run/docker.sock`. On native Windows, the exact local `dockerDesktopLinuxEngine` npipe is sufficient Docker Desktop evidence only when the daemon OperatingSystem probe is unavailable, so Docker Desktop's inspect-only `/var/run/docker.sock.raw` alias remains joinable during stopped-container restart; a successful non-Desktop daemon identity, TCP, SSH, generic or foreign npipe endpoints, native or remote Docker, and Podman do not gain that alias trust. Other daemon-reported host source representations are deferred only for an already-running managed container after they are proven to target the current Docker daemon, because joining cannot change that immutable mount or expand its existing privilege. Project identity or mount-destination substitution, privilege expansion, unexpected host devices, and any unknown mount destination remain fail-closed. Container liveness alone must not be reported as evidence of active CCC sessions.
    The immutable container-manager socket proof runs the in-container daemon identity query explicitly as root under the already privileged host container-manager operation, so interactive-user socket permissions cannot turn an equivalent Docker Desktop proxy source into an unknown result. It still requires an exact match to the host daemon identity; failed, malformed, unavailable, or foreign results remain fail-closed.
    Container running state is not command readiness. Every command session, including a session joining a container that another CCC process has just started, must acquire a distinct bounded per-container setup lock and verify or install its requested tool before attempting the final exec. A simultaneous joiner waits for the current setup owner and then performs the same idempotent readiness check; setup-lock timeout or failure must abort rather than execute an unverified or missing command. This setup lock must remain separate from the container lifecycle lock so setup-time restart recovery cannot deadlock by reacquiring lifecycle authority.
    Worktree paths use independent project, container, and session namespaces derived from their stable lexical absolute paths. Canonical host filesystem identity, including equivalent Windows path aliases, is used only to validate that those namespaces and sources belong to the expected repository; ambiguous or denied Windows canonical-path observation fails closed before lifecycle mutation. Explicit `@branch` launches and commands started directly inside unified or multi-repository worktrees use the same branch guard and project-family lifecycle lock, while malformed or mixed worktree metadata is rejected rather than treated as a regular project. A requested branch that is absent locally and on `origin` is created from each managed repository's current HEAD. Initialized tracked submodules are represented by independently owner-verified linked worktrees on the requested branch, including recursive tracked submodules; workspace creation must not checkout, reset, rebase, clean, or otherwise mutate the source submodule working tree, and an unavailable source submodule repository fails without initializing it implicitly. Container mount discovery uses the owner-verified source repository inventory to preserve initialized tracked submodules and non-ignored nested repositories reported by Git even when workspace-local discovery metadata is stale, while arbitrary ignored standalone repositories are never rediscovered. For absorbed and old-form embedded submodule metadata, CCC converts Windows-created linked-worktree `.git` forward pointers to portable relative references, mounts the verified common Git directory, preserves the host-valid `worktrees/<name>/gitdir` registration, and supplies only the compatibility workspace mount required for that registration to resolve from the nested repository inside Linux without a `prunable` worktree entry. Git repositories located only beneath ignored paths are not discovered or managed automatically and remain untouched in source and worktree lifecycle operations. `git show-ref --quiet --verify` exact-ref status distinguishes documented missing status `1` from spawn failures and other fatal Git inspection failures on every supported platform. Session registration and preparation are serialized against workspace removal. Stop and removal revalidate every independently managed worktree repository's exact checked-out branch and source-repository ownership, include every profile session and container, require exact CCC-managed canonical project labels, and pin destructive runtime commands to inspected container IDs so a foreign same-name container, unrelated same-branch directory, base repository, or sibling worktree cannot be targeted.
    Fail-closed startup diagnostics must identify whether automatic stopped-container replacement was denied by state proof or live/indeterminate session claims, and bind-identity failures must name the exact container mount destination that failed proof without weakening the underlying decision. If the primary Windows process/start-token observation is unavailable or inconclusive, CCC may use only a verified System32 process enumeration to prove that a recorded PID is absent. PID presence keeps a legacy lock active but leaves a V2 lock indeterminate and preserved. Empty, partial, malformed, or extra-field output, stderr, nonzero exit, timeout, spawn failure, or failure to verify the canonical executable preserves the ownership claim.
5. **Tool version management** — mise-based per-project tool versions
6. **Browser testing** — Chromium included for headless testing
7. **Network transparency** — `--network host` for direct port access, localhost proxy for Docker Desktop / podman machine
8. **Tool credential availability** — every local container mounts all registered coding-tool credential directories regardless of the command or tool that starts it
9. **Stable credential config ownership** — `~/.ccc/*` credential directories and generated config files remain writable across host/container boundaries. `ccc` avoids routine `chown`/`chmod` churn on mounted Codex config files; it checks container access first and only attempts in-container access repair when the in-container user cannot read/write the mounted config. Permission failures must surface with an actionable ownership repair instead of a raw stack trace
10. **Actionable Hyper-V provisioning diagnostics** — Windows and Linux VM provisioning keeps command input and raw output redacted while preserving allowlisted, stage-specific failure codes for PowerShell loading, VM identity/state checks, credentials, SSH keys, paths, and ISO media. Provisioning command changes advance the broker capability contract so a host cannot silently reuse an older broker implementation.
11. **Bounded Android emulator storage** — deleting a CCC-provisioned Android emulator removes both its AVD registration and its exact owner-prefixed `.avd` data directory. Durability recovery inspects the configured Android AVD storage directly as well as `avdmanager` inventory, so interrupted or partially registered E2E AVDs are reclaimed. Cleanup is fenced to the current 16-hex owner namespace, immediate AVD-home children, regular `.ini` files, and non-symbolic `.avd` directories; user AVDs, other owners, traversal names, and symbolic artifacts are preserved or rejected.
12. **Self-contained Unix global installs** — a source-repository global install owns one `ccc-dist` package root containing sibling `dist/`, `device-lab-mcp/`, and `scripts/` trees plus the container build files required at runtime. The `ccc` launcher imports `ccc-dist/dist/index.js`, preserving the same package-relative module resolution used by the published npm package. Reinstall replaces that package root as one unit, and uninstall removes the launcher and that single owned tree.
