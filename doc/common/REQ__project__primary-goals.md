# Primary Goals

Run Claude Code in isolated containers with:

1. **Per-project isolation** — containers named by path hash, each project gets its own environment
2. **Runtime-agnostic container execution** — works with Docker or Podman; auto-detect with Podman preferred, override via `--runtime` / `CCC_RUNTIME`. First-class support for rootless Podman on Linux and podman machine on macOS/Windows (added 2026-04-17)
3. **Host environment forwarding** — auto-forward env vars, SSH agent, locale, timezone
4. **Session lifecycle management** — lock files track sessions, auto-stop the container when the last joined session exits, and never automatically replace a running project container, including when the current CLI owns the only session lock. Every automatic replacement path must revalidate both process identity and an explicit successful stopped-container probe under the shared container lifecycle lock; unknown, timed-out, access-denied, and failed runtime probes fail closed. Replacement removes an already-stopped container without first issuing `stop`, so a concurrent external start aborts removal. V2 session locks use OS process start-token observation as the primary liveness authority: only an explicit process-missing result or token mismatch removes a stale lock, while empty, malformed, unavailable, timed-out, access-denied, and failed observations preserve it. If start-token observation is unavailable during session creation, CCC must remain joinable by writing a conservative legacy PID lock instead of rejecting the session. Legacy PID-only locks are stale only on explicit `ESRCH`; all other uncertain probe failures preserve ownership. A lock directory that disappears or becomes unreadable after initialization must fail closed rather than represent an empty session set. Session cleanup and the clipboard watchdog share one lock parser and liveness implementation. Session lifecycle code retains lock-deletion authority under the owning container lifecycle lock; the global clipboard watchdog may only aggregate lock liveness without mutation and shuts down the singleton server after its no-session grace period. Closing one of multiple live sessions must never stop their shared container, including when Windows PID signal probing would return a false negative. Immutable mount/image contract updates are deferred until the container has stopped. A running CCC-managed container with the exact normalized project identity label and expected writable project mount destination remains joinable while missing additive credential, Git, VM, or device-broker mounts and non-authority environment differences are deferred. The project source must match the canonical host path or a recognized equivalent Windows/Docker Desktop representation. Existing non-project bind mounts must retain their expected source, type, and access, named volumes must retain their expected source, and obsolete authority-bearing mounts must be absent; credential, broker-auth, container-socket, SSH, Git, and configured extra-mount substitution fail closed. Project identity or mount-destination substitution, privilege expansion, unexpected host devices, and any unknown mount destination remain fail-closed. Container liveness alone must not be reported as evidence of active CCC sessions.
   Worktree paths use independent project, container, and session namespaces derived from canonical host filesystem identity, including equivalent Windows path aliases; ambiguous or denied Windows canonical-path observation fails closed instead of creating another lifecycle namespace. Explicit `@branch` launches and commands started directly inside unified or multi-repository worktrees use the same branch guard and project-family lifecycle lock, while malformed or mixed worktree metadata is rejected rather than treated as a regular project. Session registration and preparation are serialized against workspace removal. Stop and removal revalidate every independently managed worktree repository's exact checked-out branch and source-repository ownership, include every profile session and container, require exact CCC-managed canonical project labels, and pin destructive runtime commands to inspected container IDs so a foreign same-name container, unrelated same-branch directory, base repository, or sibling worktree cannot be targeted.
5. **Tool version management** — mise-based per-project tool versions
6. **Browser testing** — Chromium included for headless testing
7. **Network transparency** — `--network host` for direct port access, localhost proxy for Docker Desktop / podman machine
8. **Tool credential availability** — every local container mounts all registered coding-tool credential directories regardless of the command or tool that starts it
9. **Stable credential config ownership** — `~/.ccc/*` credential directories and generated config files remain writable across host/container boundaries. `ccc` avoids routine `chown`/`chmod` churn on mounted Codex config files; it checks container access first and only attempts in-container access repair when the in-container user cannot read/write the mounted config. Permission failures must surface with an actionable ownership repair instead of a raw stack trace
